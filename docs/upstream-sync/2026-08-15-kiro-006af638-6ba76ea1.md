## Preserved local invariants

- Direct KIRO and Anthropic-compatible relay accounts remain separate; relay
  accounts with `base_url` continue through the shared gateway.
- Q chat uses body `profileArn`; Q MCP uses
  `x-amzn-kiro-profile-arn`; KRS keeps both with the existing fallback.
- Persisted machine IDs and account-scoped token/cache identity remain stable
  across refresh-token rotation.
- API region and IDC login region are independent as described above.
- Local provider-native capture, redaction, strict terminal validation,
  pre-output failover, committed-partial handling, exact-once usage, KIRO
  credits, and cache presence semantics remain authoritative.
- Cache planning does not mutate tracker state before success. Direct 2xx and
  the first successful WebSearch provider iteration are the commit boundaries;
  failures leave the next identical request as cache creation.
- Compaction prompt/replay conversion is explicitly enabled only for a selected
  KIRO account. A non-KIRO first selection retains its historical unknown-item
  behavior. Once mixed scheduling selects KIRO for a compaction request, later
  failover is restricted to KIRO so the client cannot receive an ordinary
  Responses success in place of the required compaction item.
- The KIRO-only failover requirement is an additional filter, not a replacement
  platform. Anthropic mixed entry semantics remain active, so only KIRO accounts
  with `mixed_scheduling=true` are eligible. DB, snapshot, load-aware, routing,
  sticky, legacy, and cooldown-retry paths preserve this rule; snapshot reads
  also revalidate the flag defensively against stale cache state.
- No production environment, live account, or real upstream provider request
  was used during implementation or verification.

## Review and publication

The first independent full-range review rejected the candidate for four
specific gaps: Chat Completions still used the old mimicry predicate; edit and
reauth could overwrite legacy runtime-region fields; IDC controls did not
expose the 34-region catalog; and KIRO remote compaction had no replay-safe
keepalive. Commit `ec70589fb` addresses all four with focused regression tests.

The second independent fixed-baseline review examined all 61 files in
`05d8f0e..a73da23` and rejected that candidate for three additional gaps:
service-level network/non-failover errors could append JSON after an SSE
heartbeat, non-KIRO accounts could receive the KIRO compaction prompt/replay,
and cache prepare could refresh a hit's expiry. Commit `e0bb90537` addresses all
three with focused regressions. During remediation, mixed scheduling exposed a
further boundary: an Anthropic entry group can select KIRO. Keepalive therefore
starts lazily from the actual selected account, and once KIRO compaction begins
the selection context is locked to KIRO for subsequent failover attempts.
