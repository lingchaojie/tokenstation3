## 发布前修复阶段（2026-08-13～15）

此前的两轮独立审查均在推送前发现问题并阻止发布。固定上游范围没有改变；后续修复仍属于本次语义同步。第四轮审查按真实 router、真实 provider recorder 和最终 side effect 逐入口复核，主要收敛如下。

### 最终 provider attempt 与敏感信息边界

- 成功和最终失败只归档实际观察到的最终上游 HTTP attempt。没有 attempt bridge、没有最终 provider request，或仅有兼容入口请求时一律 fail closed，不伪造 provider-native 记录。
- redirect、transport replacement、retry、账号 failover 和 WebChat direct 路径统一保存最终 request body/hash/model/stream、最终 endpoint、脱敏 headers、provider request-id 与原始 response。成功、committed partial 和 terminal error 均 exact-once；被放弃的中间账号不计费、不归档。
- KIRO direct、WebSearch、Chat Completions、Responses 和 WebChat 保存最终 AWS request envelope 与原始 AWS EventStream；不再用转换后的 Anthropic JSON/SSE 覆盖。AWS frame JSON、长度、headers 和 CRC 均严格校验。
- endpoint 会删除 URL userinfo 和 API key、token、credential、secret、password、signature、OAuth code、SAS 等敏感 query；任意 custom header 的 credential marker 同样脱敏，同时保留标准 request-id/rate-limit 等诊断头。
- provider request/response 正文各自硬上限 8 MiB；超出保留精确前缀并标 `Truncated=true`。该存储上限不再限制业务读取或 Bedrock frame 解析。`max_queue_bytes` 必须为 `0` 或至少 `2 × max_body_bytes`，headers 也计入预算。
- capture 静态关闭或运行时策略未命中时不创建 attempt slot，也不扫描或快照 capture 正文。策略命中但 raw 内容列关闭、或需要在 8 MiB 前缀之外提取最终 provider 元数据时，使用有界 scanner/hash；大 scalar、dense JSON 和 final replacement request 均有内存上限回归测试。

### 流式终态、failover 与计费三态

- Anthropic、Bedrock、OpenAI Responses/Chat Completions、Gemini/Antigravity 和 KIRO 都按明确状态机区分：首个可消费语义前协议损坏可安全 failover；已提交语义后的异常返回 partial terminal；合法完整终态才成功。
- provider frame 的 JSON/envelope/type/known-field shape、event/data 一致性、start/block/stop 顺序和 terminal 后数据均校验；未知但带非空字符串 type 的扩展保持前向兼容。
- 普通空 `stop`/`length` choice、role-only、仅 framing/usage/metadata、empty candidate 与 malformed tool/function call 不再单独证明成功；官方 `content_filter`、provider block 和 KIRO explicit stop-only 等明确协议终态仍按各自 wire contract 接受，不重复换号。
- first-output staging 与客户端 commit 边界统一；pre-semantic keepalive/preamble 不阻止换号，stage 溢出和 reader/scanner/idle 错误不会伪装为客户端断开。committed partial 仍保留 usage、调度失败语义和 terminal capture。
- real two-account recorder 已覆盖 Anthropic ordinary/API-key/compat、Bedrock、OpenAI native/passthrough/compat、Gemini native/compat、Antigravity native/base-url/collector、KIRO direct/compat/WebSearch；断言只有最终成功账号产生 capture/usage。单账号 malformed HTTP 200 终态用例断言原始 provider bytes/status/headers 精确归档。

### 其他发布修复与明确取舍

- Audit `ClearAll` 增加本进程 writer barrier、事务锁与 rollback 测试。正式部署当前必须保持单 backend replica；多副本会有另一实例的 pre-clear 内存队列在清理后重新写入，扩容前必须实现分布式 clear epoch/barrier。
- 管理设置更新保留 omitted Passkey/Session Binding/Step-up 字段，避免旧客户端提交部分 payload 时把隐藏配置归零。
- 支付退款的原子状态、rollback、commit 后 cache invalidation、EasyPay UTF-8 与 1 MiB 边界保留；支付宝 mobile precreate deep-link 明确不合入，移动端继续使用既有 WAP/App 跳转。
- 生成物使用仓库既有生成流程更新；不采用额外的 SuperPower/SDD 发布流程。
- 发布工具链从 Go 1.26.5 升至 1.26.6；1.26.5 的标准库被 fresh `govulncheck` 命中 6 个可达漏洞，Docker 构建与 CI 精确版本检查同步到 1.26.6。
