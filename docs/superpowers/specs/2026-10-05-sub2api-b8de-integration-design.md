## 组件与数据流约束

### 网关、预留与结算

在现有鉴权、统一 Key、有效分组和可用资金校验之后，才允许按开关登记 Redis
在途预留；估价不是实际扣费。启用后估价和可用资金范围必须匹配本地最终定价、
奖励资格及订阅回退路径，不能把不可使用的奖励余额当作可用普通余额。
预留句柄随请求及异步计费任务交接，覆盖取消、流结束、failover、计费提交失败
和续期清理；实际扣费仍由本地幂等结算执行。

保留上游预留算法的边界：无其他在途预留时允许首请求通过既有余额预检，
Redis 不可用时不增加拒绝，无法估价默认不预留，可显式配置拒绝无法估价请求。
这不是严格防透支保证，也不能放宽本站既有缺价拒绝规则。默认关闭时请求行为
必须与当前 dev 一致。简易模式不引入账户 / 用户 / 订阅扣款。

保留真实结算 BillingType 与订阅所属组驱动缓存更新，不以预估计费模式替代。
请求中途删除 Key 的上游结算修复须继续处理用户实际费用，但不能吞掉其他数据库
错误或破坏统一 Key、额度及幂等事务。媒体入口既有利润门豁免不扩展、不取消。

共享协议修复覆盖 Responses / WS / Chat、Gemini / Antigravity、工具参数、
思考设置、终止 / 取消状态和空响应 failover。保留 KIRO direct / relay、
machine ID、ARN、credits、sticky / cooldown，以及 capture 最终真实 attempt、
spool 和 WebChat 的清理与记录路径；遵循 `docs/kiro-upstream-sync.md`。

### 充值、订单与数据库

下单时快照优惠结果：到账总额含赠金，`bonus_amount` 单独记录免费额度；
支付币种实收与手续费分开，订阅订单不参与充值优惠。后续修改活动不重算已建订单。
成功支付沿本地既有幂等履约链入账，邀请奖励基数排除免费部分，签到 / 邀请奖励
的发放、到期、消费顺序保持原实现。退款继续沿本地既有订单金额与实收比例及
退款状态机处理，不把免费赠金按面值额外退成现金；发现需改变退款或奖励回收
规则时停止该处实现并询问，不暗中制定新政策。

246 使用 `bonus_amount DECIMAL(20,2) NOT NULL DEFAULT 0`，旧订单不增加赠金。

### TypeSafe 与管理安全

System One 使用独立原生协议，不误入聊天协议转换；接入本站鉴权、统一 Key、
审核、计费、平台额度和错误处理链，不复活 Composite 依赖。
后台账号 / 分组 / 渠道、前端平台枚举、API 类型及模型展示保持契约一致。
既有内部 TypeSafe 审核配置不会因新平台入口而被重写。

风控白名单只豁免已批准的本地风控效果，异步任务携带请求时的审计模式，
不能意外执行封号或通知。设置缓存失败与名单移除路径必须测试；不能改变
普通用户、上游拒绝、API Key 认证或余额 / 额度的处理。

Claude 手动重置仅挂管理路由，使用持久化幂等记录及账号 / 组织锁，防止同组织
多个本地账号重复消费。上游结果不明时按上游 24h 防重窗口处理，明确不可用
按 15min 窗口处理；数据库或锁存储缺失时拒绝兑换，不以失败重试再次消耗。
查询本身不兑换；保留代理、身份及敏感标识清理，测试不访问真实账号。
