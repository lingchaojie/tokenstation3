# 普通用户更新公告与公告设置整合设计

- 日期：2026-08-20
- 状态：已确认，待实施计划
- 范围：复用现有公告系统，重做普通用户弹窗 UI，并将滚动公告配置迁入管理员左侧“公告设置”页面

## 1. 背景

仓库已经存在完整的公告能力：

- 管理员路由 `/admin/announcements` 及公告新增、编辑、删除、预览和阅读统计页面；
- 管理员公告 CRUD API；
- 普通用户公告列表及服务端已读 API；
- 公告草稿、发布、归档、弹窗/静默模式、起止时间和用户范围；
- 前端弹窗队列、右上角公告铃铛和 Markdown 安全渲染；
- `announcement_banners` 与 `announcement_banner_interval_ms` 两个滚动公告设置。

本期不新建公告子系统，也不覆盖现有路由或接口。目标是把现有能力整理成清晰的管理员入口，并让普通用户公告弹窗沿用站内引导弹窗的视觉语言。

管理员首次登录的 onboarding 指引由 `driver.js`、`useOnboardingTour` 和 `components/Guide/steps.ts` 驱动，与公告系统相互独立。本期只参考其卡片层级和交互表达，不修改它的逻辑、存储键或接口。管理员合规确认弹窗同样不在本期范围内。

## 2. 已确认的产品决策

1. 管理员左侧导航中的现有“公告”入口改名为“公告设置”，继续使用 `/admin/announcements`。
2. 公告设置是独立的左侧导航页面，不是“系统设置”页面内部的顶部 Tab。
3. 公告设置页面包含两个纵向区域：
   - 上方：现有更新公告管理；
   - 下方：从系统设置迁来的顶部滚动公告配置。
4. 普通用户弹窗采用已确认的 A 方案“品牌引导卡”：站点 Logo、站名、公告图标、标题、Markdown 正文、发布时间、多条进度和操作按钮。
5. 多条未读弹窗公告按现有服务端顺序组成一轮队列；按钮显示“下一条”，最后一条显示“知道了”。
6. 点击“下一条”或“知道了”把当前公告记为已读。服务端已读后，不再自动弹出该公告。
7. 点击右上角关闭或“稍后阅读”只结束当前弹窗轮次，不标记任何未处理公告为已读；之后仍可从公告铃铛查看，下一次会话仍可提醒。
8. 管理员可以在公告设置页面预览用户弹窗；管理员首次登录指引不受影响。

## 3. 方案选择

### 采用：扩展现有公告页面

保留 `/admin/announcements`、现有公告数据库表、服务层、API 和管理页面，在现有页面底部加入滚动公告设置卡片，并重做 `AnnouncementPopup.vue`。

优点：

- 不迁移公告数据，不产生两套公告来源；
- 阅读状态、用户范围、定时发布和 Markdown 清洗全部复用；
- 旧链接、书签和 API 客户端保持兼容；
- 实施范围以已有前端整合为主，风险最小。

### 未采用：新建第二套“更新公告”设置

该方案会与现有 `announcements`、`announcement_reads` 和管理 API 重复，并导致管理员需要判断两套公告的用途，因此不采用。

### 未采用：把完整公告管理塞进系统设置页

系统设置已经较大，公告 CRUD、筛选、阅读统计和预览也不是普通的键值设置。把它作为系统设置内部 Tab 会削弱导航层级，并与用户指定的左侧入口不符，因此不采用。

## 4. 信息架构与管理员 UI

### 4.1 左侧导航

- 保留现有侧栏项的路径 `/admin/announcements` 和铃铛图标。
- 管理员专用文案从共享的 `nav.announcements` 拆为 `nav.announcementSettings`，中文显示“公告设置”，英文显示“Announcement settings”。
- 不修改普通用户公告入口或公告铃铛文案。

### 4.2 公告设置页面

页面标题改为“公告设置”，说明为“统一管理登录弹窗与站内顶部滚动公告”。

上方保留现有公告管理能力：

- 搜索、状态筛选、服务端排序和分页；
- 新增、编辑、删除和预览；
- 草稿 / 发布 / 归档；
- 弹窗 / 静默通知模式；
- 起止时间和用户范围；
- 阅读状态统计。

下方新增独立的 `AnnouncementBannerSettingsCard`：

- 切换间隔，输入单位为秒，继续保存为毫秒；
- 中文和英文短文案；
- 添加、删除、上移和下移；
- 当前滚动条样式的即时预览；
- 独立“保存滚动公告设置”按钮和保存状态。

该卡片从 `SettingsView.vue` 迁出。系统设置页不再渲染或提交这两个字段，避免两个页面同时编辑时用旧值覆盖新值。

## 5. 普通用户弹窗 UI 与交互

### 5.1 视觉结构

弹窗继续挂载到应用根部并覆盖主页面，沿用站内圆角、细边框、暗色模式和线性图标：

1. 顶部品牌区：`site_logo` 或 `/linx2-icon.png` 回退图标、`site_name`、公告类型图标和“新公告”标识；
2. 内容区：公告标题、发布时间和经过清洗的 Markdown 正文；
3. 底部操作区：`当前序号 / 本轮总数`、进度点、“稍后阅读”和主按钮；
4. 非最后一条主按钮为“下一条”，最后一条为“知道了”。

管理员预览继续复用同一个 `AnnouncementPopup` 组件，但预览模式不写已读记录，也不进入真实用户队列。

### 5.2 展示范围

- 自动弹窗只消费 `notify_mode = popup`、当前用户可见且未读的公告；
- 已读或静默公告仍保留在公告铃铛中；
- 公告数据继续为所有登录用户加载，以保留管理员公告铃铛能力；本期只对普通用户自动展示弹窗。管理员通过公告设置页面预览内容，避免公告弹窗与管理员 onboarding 或合规确认弹窗竞争；
- 公告服务端排序保持现状：未读优先，同状态按较新的公告在前。

### 5.3 已读与关闭语义

`下一条 / 知道了`：

1. 立即从当前视觉队列前进，保持操作流畅；
2. 调用现有 `POST /api/v1/announcements/:id/read`；
3. 成功后同步本地公告的 `read_at`；
4. 最后一条处理后关闭弹窗并恢复页面滚动。

`× / 稍后阅读`：

1. 关闭本轮弹窗并清空当前弹窗队列；
2. 不调用已读 API；
3. 不改变公告铃铛中的未读状态；
4. 当前页面生命周期内不立刻重新排队，刷新或下一次会话可再次展示。

## 6. 数据流与组件边界

### 6.1 更新公告

```text
管理员公告设置页
  -> 现有 /api/v1/admin/announcements CRUD
  -> announcements 表
  -> 普通用户 /api/v1/announcements
  -> announcement store 筛选未读 popup
  -> AnnouncementPopup 逐条展示
  -> /api/v1/announcements/:id/read
  -> announcement_reads 表
```

不新增数据库迁移、公告 DTO 或公告 API。

### 6.2 滚动公告

```text
AnnouncementBannerSettingsCard
  -> GET /api/v1/admin/settings 读取现值
  -> PUT /api/v1/admin/settings 仅提交
       announcement_banners
       announcement_banner_interval_ms
  -> 现有 public settings
  -> useAnnouncementBanner
  -> AppLayout 顶部滚动公告条
```

管理员设置后端已经支持部分 PUT，并保留未发送字段。新卡片必须只发送上述两个字段，避免意外覆盖其他系统设置。

### 6.3 前端组件职责

- `AnnouncementsView.vue`：编排公告 CRUD 区和滚动公告设置卡片，不复制 API 逻辑；
- `AnnouncementBannerSettingsCard.vue`：滚动公告读取、编辑、校验、重排、预览和部分保存；
- `AnnouncementPopup.vue`：品牌化展示、序号、关闭和前进事件；
- `stores/announcements.ts`：队列位置、已读写入、关闭整轮和失败状态；
- `App.vue`：继续为登录用户拉取公告，但只允许普通用户启动自动弹窗队列；
- `AnnouncementBell.vue`：继续作为全部公告和未读公告的非阻塞入口。

## 7. 校验与错误处理

### 7.1 普通用户

- 公告列表加载失败不阻塞页面；维持现有静默降级，后续可由可见性变化或路由变化重试。
- 已读请求失败时，服务端仍保持未读。界面不重新打断当前轮次，但显示轻量错误提示：“已读状态保存失败，下次可能再次提醒”。
- Markdown 继续经 `marked` 解析并由 DOMPurify 清洗；不允许公告内容直接注入未清洗 HTML。
- 关闭弹窗、完成队列或组件卸载时必须恢复 `document.body.style.overflow`。
- 管理员 onboarding、管理员合规弹窗或其他高优先级阻塞弹窗可见时，不启动普通用户公告弹窗。

### 7.2 管理员

- 滚动公告继续沿用后端现有约束：最多 20 条、单语言最多 200 字、至少一个语言非空、间隔 1–60 秒；
- 前端在提交前显示字段级错误，后端错误通过站内 toast 展示；
- 保存期间禁用按钮，防止重复提交；
- 保存成功后使用服务端返回值回填生成的稳定 ID；
- 公告 CRUD 与滚动公告保存相互独立，其中一方失败不影响另一方已经保存的数据。

## 8. 兼容性与迁移

- `/admin/announcements` 路由保持不变；
- `/api/v1/admin/announcements*` 与 `/api/v1/announcements*` 保持不变；
- `announcements` 和 `announcement_reads` 表保持不变；
- `announcement_banners` 与 `announcement_banner_interval_ms` 的存储键、数据格式和公开下发保持不变；
- 已有滚动公告无需数据迁移，部署后会在新页面原样显示；
- 已有公告和已读记录不受影响；
- 管理员 onboarding 的 localStorage key、步骤和样式保持不变。

## 9. 测试策略

### 9.1 普通用户弹窗

- 只把未读且 `notify_mode = popup` 的公告加入队列；
- 多条公告显示正确的 `1 / N`、`2 / N` 和最终按钮文案；
- 点击“下一条”只标记当前公告已读并展示下一条；
- 点击“知道了”标记最后一条已读并关闭；
- 点击 `× / 稍后阅读` 不调用已读 API，并结束当前轮次；
- 已读请求失败时下一条仍可展示，同时保留服务端未读语义并给出提示；
- 已读公告在下一次获取时不会重新自动弹出；
- 站点名称、站点 Logo、默认 Logo和暗色模式正确；
- 管理员预览不调用已读 API；
- 弹窗关闭、完成和卸载均恢复 body 滚动；
- 管理员不会被普通用户公告自动弹窗打断。

### 9.2 公告设置页面

- 左侧管理员入口显示“公告设置”，路径仍为 `/admin/announcements`；
- 现有公告搜索、筛选、排序、分页、CRUD、预览和阅读统计回归通过；
- 滚动公告卡片正确加载、添加、删除、排序和双语编辑；
- 保存请求只包含两个滚动公告字段；
- 后端部分更新不会覆盖其他设置；
- 设置页面不再提交滚动公告字段；
- 保存后 AppLayout 的顶部公告使用新值和新间隔；
- 原有滚动公告数据无需迁移即可回显。

### 9.3 后端回归

本期原则上不修改公告后端。运行现有公告 service、handler、repository 和设置 partial-payload 测试，证明路由、权限、用户范围、已读记录和部分设置更新未被前端整合破坏。

## 11. 非目标

- 不重写公告后端或创建第二套公告表；
- 不更改管理员首次登录 onboarding；
- 不更改管理员合规确认弹窗；
- 不为滚动公告新增链接、富文本或服务端已读状态；
- 不新增公告邮件、短信或第三方推送；
- 不改变公告用户范围规则；
- 不改变现有普通用户公告铃铛和历史公告列表的职责。

## 12. 完成标准

1. 管理员左侧可通过“公告设置”进入原 `/admin/announcements` 页面；
2. 页面同时包含完整更新公告管理和滚动公告配置；
3. 系统设置页不再出现或提交滚动公告字段；
4. 普通用户看到确认的 A 款品牌公告弹窗；
5. 多条公告可以逐条前进，已读后不再自动弹出；
6. 关闭或稍后阅读不误记已读；
7. 原有公告、已读记录、滚动公告数据、管理员 onboarding 和全部现有接口保持兼容；
8. 针对新交互的前端测试及现有相关回归测试通过。
